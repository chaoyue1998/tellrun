# Agent Relay 产品需求文档

本产品供本人通过 Telegram 私聊，操作服务器项目中的 Codex：提交任务、继续对话、查看进度、处理审批和停止执行。首版以稳定完成这条交互链路为目标。

已确认约束：Node.js + TypeScript；个人使用；先接 Telegram 和 Codex；后续逐步接入其他 IM 与 Claude 等 Agent。已按技术方案开始搭建基础框架，下文为首版产品目标；当前实现范围见项目 README。版本为 v0.1，日期为 2026 年 10 月 28 日。

[架构与技术选型](architecture.md)

## 产品目标与首版边界

用户离开电脑后，仍可在手机上继续服务器里的开发任务，并清楚知道任务的工作目录、是否仍在运行、是否等待自己处理。

首版建议采用单台 Linux 服务器、一个 Telegram Bot、一个授权用户，入口限定为私聊。Linux 是部署建议，具体发行版与架构在实施时核对。

| 范围 | 首版决定 |
| --- | --- |
| 用户 | 本人；以 Telegram 数字用户 ID 授权 |
| IM | Telegram 私聊，长轮询 |
| Agent | Codex；复用服务器上的登录与配置 |
| 工作目录 | 由任务或会话指定，不设置项目清单或目录白名单 |
| 会话 | 可新建、选择和继续多个 Agent 会话 |
| 执行 | 全局同时执行一个编码任务；普通新消息排队 |
| 交互 | 文本、进度消息、审批按钮、补充问题、停止任务 |
| 部署 | 一个 Node.js 常驻服务，由 systemd 管理 |

图片、语音、通用文件传输、群聊与论坛话题、Web 管理界面、定时任务、多人权限及计费放在后续版本。其他 IM 和 Claude 等 Agent 分别按实际需求增加。

## 核心使用流程

1. 首次私聊机器人，进入或新建 Agent 会话。

2. 在任务中指定工作目录，后续对话可沿用该会话的目录。

3. 用户发送任务，收到“已接收”或“排队中”的回执。

4. 执行期间，机器人更新同一条进度消息；内容包含当前阶段、工具活动摘要和耗时。

5. 需要授权时，机器人发送审批消息；需要澄清时，发送问题和可选答案。

6. 用户批准、拒绝、补充输入，或停止任务。

7. 完成后收到结论、修改摘要、实际执行的检查及未完成事项；后续消息可继续该会话。

示例：发送“在 /srv/my-site 中分析登录失败的原因” → 查看分析 → 发送“按这个方案修复” → 处理需要授权的操作 → 查看结果。无需事先登记目录或选择项目。

## 首版功能要求

| 编号 | 功能 | 用户可见行为 | 验收条件 |
| --- | --- | --- | --- |
| P0 01 | 本人授权 | 只有配置的本人可操作机器人 | 其他用户的消息和按钮回调均不能创建任务、读取结果或批准操作 |
| P0 02 | 工作目录 | 直接指定任务工作目录 | 无需预先登记目录；已排队任务保留提交时的目录 |
| P0 03 | 会话管理 | 新建、列出、选择和续聊 | 两个会话不串上下文；正常重启后可继续已保存的会话 |
| P0 04 | 任务排队 | 显示等待状态，可查看和取消待执行任务 | 同一时间最多一个编码任务；排队数据可在重启后读取 |
| P0 05 | 进度与结果 | 更新进度，最终给出明确结果 | 成功、失败、主动停止和异常中断分别展示 |
| P0 06 | 执行审批 | 显示操作及允许或拒绝按钮 | 按钮只作用于对应操作；过期和重复点击不产生额外执行 |
| P0 07 | 补充问题 | 显示选项，支持明确回复问题 | 答案进入对应问题；其他普通消息仍排队 |
| P0 08 | 停止任务 | 显示“正在停止”，随后给出停止结果 | 停止指令不被编码任务阻塞；未确认结束前不显示“已停止” |
| P0 09 | 故障恢复 | 展示异常中断及后续处理入口 | 不自动重放执行结果不确定的任务 |
| P0 10 | 服务状态 | 查看当前会话、工作目录、任务、队列和连接状态 | 编码任务执行或等待审批时，状态查询仍能响应 |

## 命令与消息体验

| 入口 | 行为 |
| --- | --- |
| /start 或 /help | 展示使用说明、当前会话和常用操作 |
| /new | 新建 Agent 会话 |
| /sessions | 分页列出会话，点击切换 |
| /status | 显示当前会话、工作目录、运行中的任务、队列和服务状态 |
| /queue | 查看排队任务，通过按钮取消指定任务 |
| /stop | 停止当前聊天的活动任务，并暂停该聊天后续队列 |
| 普通文本 | 作为当前会话的新任务；忙碌时进入队列 |
| 审批或问题按钮 | 立即处理，不进入编码任务队列 |

停止后提供“继续排队”和“清空队列”按钮。已接收任务保留提交时的会话与工作目录。存在问题时，只有点击选项或明确回复该问题消息才作为答案，避免把另一条需求误当作审批或答案。

进度默认每 2 秒最多更新一次，重要的等待审批、失败和完成状态优先发送。首版使用纯文本和按钮；长回复按 Telegram 限制拆分并标记顺序，保留完整结果供再次查看。模型表达的结论和程序确认的任务状态分开处理：只能依据执行事件判断是否完成，不能仅因回复里出现“完成”就标记成功。

Telegram 支持长轮询，服务器主动接收更新；这种部署方式无需公开 Webhook 接收地址。[grammY 部署说明](https://grammy.dev/guide/deployment-types)

## 审批与异常行为

默认建议使用 Codex 的工作区写入权限与按需审批策略。允许范围内的操作可直接执行；只有 Codex 明确发起的审批请求才显示审批交互，因此不是每一条命令都弹出按钮。操作范围受运行时实际配置和托管策略约束。[Codex 审批说明](https://learn.chatgpt.com/docs/app-server#approvals)

| 情况 | 产品行为 |
| --- | --- |
| 需要执行授权 | 显示工作目录、操作内容和原因；提供本次允许、拒绝、停止任务 |
| 需要补充信息 | 展示问题；选项或明确回复可作为答案 |
| 审批超时 | 使按钮失效并说明原因；拒绝该请求或停止等待，按请求类型处理 |
| 重复或旧按钮 | 提示已处理或已失效，不再次执行 |
| 用户拒绝操作 | 将拒绝交给 Codex；若它继续提出可行方案，保持当前任务 |
| 用户停止 | 请求中断；终态确认前保持“正在停止”；无法确认时显示异常中断 |
| Telegram 暂时断线 | 服务保留任务状态；恢复后补发必要的结果或待处理通知 |
| Codex 进程异常退出 | 将活动任务标记异常中断，保留上下文和错误信息 |
| 服务重启 | 恢复排队记录和会话；对执行状态不确定的任务提示先检查结果 |
| 收到重复消息事件 | 复用已有任务记录，不重新执行编码任务 |

正常重启后可恢复会话，不代表执行中的任务能无缝继续。结果不确定时，先展示已有记录，再由用户明确选择继续或重新提交。

## 数据与运行要求

任务使用用户指定或当前会话沿用的工作目录，Relay 不限制项目目录，也不要求项目配置文件。会话绑定、任务状态、待处理交互和发送记录保存在服务器本地；Codex 原生历史由 Codex 管理。恢复服务需要同时保留应用数据库和相应 Codex 会话数据。

聊天文本通过 Telegram 传递，模型请求按 Codex 配置发往相应服务。Bot Token 等凭据从服务环境或受限配置读取；日志默认记录任务标识、状态和错误类别，不记录凭据及完整聊天正文。

以下是首版验收目标，执行时延不包括模型生成耗时及外部网络故障：

- 正常网络下，收到消息后目标 2 秒内给出接收或排队反馈。

- 编码任务运行时，状态查询、审批和停止仍可处理。

- 在两个工作目录中使用不同会话，消息、审批和结果归属正确。

- 重复投递同一消息，不增加第二个编码任务。

- 重启后保留会话与排队任务；不自动重跑曾经开始且结果不确定的操作。

- 运行 24 小时并完成一次网络恢复、一次进程故障演练后，能够继续处理新任务。

## 实施阶段与扩展方向

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0 协议验证 | 在目标 Linux 环境验证 Codex 的会话、事件、审批、提问和中断 | 固定可用的 Codex 版本及协议类型，关键交互通过 |
| M1 基础链路 | Telegram 私聊、本人授权、会话、任务与结果 | 可以在指定工作目录执行任务并继续对话 |
| M2 可用首版 | 多会话、排队、审批、停止、故障恢复 | P0 功能与异常验收通过 |
| M3 日常运行 | systemd 部署、备份、日志、长时间运行检查 | 可以作为个人日常工具使用 |
| 后续 IM 扩展 | 增加一个实际需要的 IM | 原有 Codex 与任务流程保持一致 |
| 后续 Agent 扩展 | 接入 Claude 等新的运行时 | 先核对其会话、审批和停止能力，再实现对应适配 |

产品名称暂用 Agent Relay。服务器系统、部署目录及首个扩展对象在相应实施阶段确定。当前不提供项目列表或项目选择流程。
